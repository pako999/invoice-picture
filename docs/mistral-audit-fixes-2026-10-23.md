# Mistral OCR audit fixes — 23 October 2026

Baseline: `5584487` ([audit](mistral-integration-audit-2026-10-23.md)). These changes implement the confirmed integration fixes. They do not remove the annotated invoice schema, evidence, validation, invoice grouping, or original documents. UI layout, prices, plans and payment flows are unchanged.

## Implemented in order

| Step / audit finding | Change and code | Effect and limits |
| --- | --- | --- |
| 1 / measurement | Existing opt-in `trace.ts` also covers document Batch polls/downloads, `provider_queue_wait` for shared-slot admission and `provider_batch_wait` for provider queue/processing timestamps. Production server/browser diagnostics are enabled through configuration; no content, signed URL, filename or key is emitted by the tracer. Provider-only benchmark remains explicit and billable. | Separates provider headers/body, parsing, persistence and first usable browser result. The legacy annotated timer is renamed `mistral_annotated_operation` because it now includes admission/accounting as well as the complete response. Use `ocr_ttfb` for the HTTP header boundary. |
| 2 / floating model | `mistral-config.ts` pins OCR to `mistral-ocr-4-1` and classification/extraction to `mistral-small-2603`; floating default aliases and retired OCR 4.0 resolve to supported pinned IDs. Production model configuration is set explicitly. | Reproducible request versions; no direct speedup claimed. Explicit other model overrides remain possible. |
| 3 / inline payload | `invoice-inline-upload.ts`, both scan pages, `/api/send`, `/api/invoice-reader`: inline source cap 2.5 MiB, serialized JSON budget 4,000,000 B; larger PDFs take existing private storage. Known oversized API requests return 413. Child fallback OCR now sends its valid signed URL directly instead of downloading/re-encoding the PDF. | Prevents payload-limit failures and removes a redundant fallback download/Base64 conversion. The measured 84 KB invoice was already a reasonable inline input. |
| 4 / concurrency | `upload-pool.ts`: three upload admissions, one for free accounts, stop new files on quota rejection and preserve outcomes for in-flight files. `provider-slots.ts` and migration 0017 enforce three provider requests across app instances, configurable 1–10. | More predictable multi-file throughput, without an unbounded `Promise.all`. Connection pooling remains native global fetch. Active requests wait at most 20 seconds for capacity; no new idle polling. Actual organization limits still determine safe concurrency. |
| 5 / whole PDF | `service.ts`, bulk config/worker: whole original PDF up to the existing 500-page technical guard by default, restricted by entitlement, available pages or an explicit provider-tier override. One-page fallback remains after 429. Returned page coverage is validated and sorted before persistence. | A 32-page successful request changes from two OCR calls to one. Low-tier/page-rate constraints can still require chunking. There is no invoice-boundary guess based on page count. |
| 6 / retries, unknown completion | `provider-errors.ts`, `mistral-http.ts`, processor, manual reprocess and bulk handlers: one automatic retry for known retryable rejection; permanent input/auth errors and ambiguous network/5xx completion stop automatic paid resubmission. `Retry-After` and operation deadlines are respected. Generic bulk stage errors stop after one deferred retry. Batch submission-intent markers survive interruption before an ID is saved. Accepted terminal batch failures retain their identity and require an explicit retry. | Removes repeat paid work and long error loops. A network/5xx response without proof of rejection may require manual review. A known stored batch ID is polled, not re-submitted. Interrupted known batches can resume polling safely. |
| 7 / quota reservations | Processor refunds rejected known-page inputs as well as unknown-page inputs. Rejected bulk ranges are released before a smaller retry. Unknown completion keeps a conservative reservation. Polling existing document batches reuses the stored original reservation; it does not reserve pages again. Run budgets decrement only after successful reservation. | Prevents internal quota inflation from definite rejections and repeated polls. Reserved estimates are not provider billing receipts; unresolved accepted work remains reserved until reconciled. |
| 8 / bulk source expiry | `provider-file.ts` and Neon `/provider-file`: key/expiry-bound, server-signed 25-hour capability; verify before storage read; stream the private source with a fresh object read. | Covers the provider's 24-hour batch window without depending on a 30-minute storage URL or static credential expiry baked into that URL. Capability access lasts up to 25 hours; do not publish these URLs. |
| 9 / cost accounting | Plain real-time OCR reserves 4,000 micro-USD/page, annotated 5,000, plain Batch 2,000, annotated document Batch 2,500. `provider-usage.ts` stores model, counters, operation, document/package, reference estimate and unknown-completion flag. Batch accounting is deduplicated by batch ID. Chat envelopes and costs are preserved; child estimates include an allocation of shared OCR/classification work. | Corrects the 25% plain-OCR reference overestimate and exposes chat/uncertain work. Unknown prices stay null. These are reference estimates, with rounding and possible provider caching/contract differences, not exact invoices. |
| 10 / scan resolution | Existing browser image resize (1600 px, JPEG 0.8) is retained; source/wire limits are enforced. No blanket PDF rasterization is introduced. | DPI cannot be inferred universally from pixel counts. No oversized 600+ DPI scan was demonstrated. Changing compression/rasterizing signed or vector PDFs without a quality set would not be a verified fix. This literal DPI criterion remains unverified. |
| 11 / DB and original email | Detail-table persistence uses one transaction/HTTP batch. OCR pages use one parameterized JSON recordset insert; classification updates use one recordset update. `original-delivery.ts` durably queues original mail independently of OCR, uses a stable Resend idempotency key, checks resolved SDK errors, and provides bounded recovery/status reporting. | Removes up to six detail-write network round trips, changes 32 page writes to one and 25 classification writes to one. Email no longer blocks the upload response and therefore the OCR wakeup. Required authorization, quotas, duplicate checks and persistence remain. |
| Volume selection | For selections of 100+ files the UI requests Batch. Inline PDFs/images use one durable annotated batch per document through `document-batch.ts`, preserving names/results; storage PDFs request the existing package Batch path. Smaller interactive uploads stay real-time. Existing one-minute Neon recovery drains both queues using one idle SQL probe. | Preserves the 50% inference discount for bulk work without merging user originals. Separate per-document batches incur more status requests than a consolidated provider batch; completion is asynchronous. Existing storage backpressure/plan limits still apply. |

## Correctness and verification

- 147 invoice tests: 144 passed, 3 skipped, 0 failed (final result recorded in PR).
- TypeScript check, production Next build and Neon worker bundle pass.
- Additional tests cover inline wire size, bounded admission and stop behavior, signed-capability expiry/tampering, pinned models, known-page refund versus unknown completion, chat estimates, body-read failures, complete page coverage, persistent Batch identity, interrupted submissions, scheduled document-batch recovery, email idempotency and SDK error results.
- Migration 0017 was exercised on a temporary Neon child branch with inherited triggers disabled and one-day expiry. Six simultaneous slot acquisitions returned exactly three distinct slots (1, 2, 3); three requests received no slot. Page-recordset insert preserved 0.98 confidence as 9800 and null confidence as null.
- No existing invoice rows are rewritten by the migration. It adds provider slots, usage records, original-email jobs and internal Batch-state fields; the document-job retry default becomes two attempts.
- Original splitting/classification and extraction regressions remain in the full invoice suite. No test sends a real invoice or email.

## Timings and remaining limits

The verified baseline remains 13,717 ms inside the Mistral HTTP operation and 16,879 ms total processing for one 83,720 B page (approximately 81% provider time). No representative live before/after benchmark was possible from this checkout: a usable local provider credential was unavailable. Mock tests and reduced request counts are not a production latency benchmark.

Run the explicit provider comparison with a permitted representative PDF and local credential:

```bash
INVOICE_OCR_TRACE=1 MISTRAL_OCR_MODEL=mistral-ocr-4-1 node --env-file=.env.local --import tsx scripts/benchmark-invoice-ocr.ts /absolute/path/invoice.pdf 3
```

This makes two billable requests/run. The plain result is only text: compare the complete extraction workflow before replacing annotated OCR. For end-to-end timing, upload the same document normally after deployment and compare the browser `end_to_end` event with server `ocr_ttfb`, `ocr_total`, `parse`, `db_write`, queue and server end-to-end events. Browser traces stay in its console; server traces stay in runtime logs. Turn diagnostics off with both trace flags set to 0 and redeploy.

Remaining provider-side latency, actual Mistral organization limits, model quality on a representative corpus, effective scan DPI, provider caching/contract prices and playground equivalence are not established by these changes. The app keeps its full annotation workload and necessary data-safety steps. There is no claim of a 1–4 seconds/page SLA or playground parity.
